выступала в роли младшего разработчика: я формулировал задачи и 
ограничения по предметной области, получал черновики архитектуры и кода,

ИИ помогал на всех этапах: проектирование структуры, генерация ORM-моделей, 
бизнес-логика (скидка, график рассрочки, машина статусов), эндпоинты, 
тесты и конфигурация CI/CD. Ревью, понимание каждой строки и финальные 
правки — на мне.

## Ключевые запросы к ассистенту

### Запрос 1 — Верификация понимания ТЗ
Перед написанием кода прикрепил PDF с заданием и попросил модель 
перечислить своими словами все требования: стек, тарифы, правила денег, 
эндпоинты, обязательные тесты и бонусы. Цель — убедиться, что я не 
упустил критичных деталей до начала работы, и синхронизироваться с 
ассистентом по предметной области.

Модель корректно вытащила все критичные правила: копейки без float, 
идемпотентность по заголовку, машину статусов и график рассрочки с 
распределением остатка в первые платежи. Расхождений с ТЗ не нашёл.

### Запрос 2 — Архитектура с учётом всех бонусов
Попросил спроектировать архитектуру сразу с учётом 5 бонусов: Docker 
Compose, HMAC-SHA256 подпись вебхуков, Alembic, фильтры GET /payments 
и GitHub Actions. Ключевые ограничения, которые зафиксировал в промпте:

- DATABASE_URL через переменную окружения: SQLite по умолчанию для 
  локальной разработки и тестов, PostgreSQL в Docker.
- Модели работают на обеих БД без изменений (VARCHAR вместо Postgres-ENUM, 
  JSON вместо ARRAY).
- Деньги строго в копейках (int), без float.
- Настройки через pydantic-settings.
- HMAC считается от сырых байтов тела запроса, сравнение через 
  hmac.compare_digest.

Модель предложила слоистую структуру `models / schemas / services / api`, 
что позволило вынести бизнес-логику в отдельный сервис и тестировать её 
независимо от HTTP-слоя.

### Запрос 3 — Бонус: HMAC-подпись вебхука
Попросил реализовать проверку подписи X-Signature (HMAC-SHA256) для 
эндпоинта webhook. Указал считать подпись от сырых байтов тела запроса 
(не от json.dumps) и сравнивать через hmac.compare_digest для защиты 
от timing-атак. Секрет брал из settings.webhook_secret.

Попутно нашёл и исправил проблему: после добавления HMAC тест 
test_invalid_transition_does_not_change_status начал падать с 401 
вместо 409, потому что запрос уходил без подписи. Добавил генерацию 
валидной подписи в тест.

## Где модель ошиблась или предложила слабое решение

### Случай 1 — Забыт индекс на поле status
**Что предложила модель:** В модели Payment добавила индекс на `email` 
для будущего фильтра `GET /payments?email=...`, но пропустила индекс 
на `status`.

**Как заметил:** В утверждённом плане было явно указано индексировать 
и `email`, и `status` для бонусного эндпоинта с фильтрами. Увидел 
расхождение при ревью сгенерированных моделей.

**Как исправил:** Добавил `index=True` к полю `status` в модели Payment 
вручную:
```python
status: Mapped[str] = mapped_column(
    String(50),
    nullable=False,
    index=True,
)
```
### Случай 2 — Модель забыла реализовать идемпотентность в роутере
**Что предложила модель:** Сгенерировала роутер `create_payment` и модель 
`Payment` с полем `idempotency_key` (с `unique=True` в БД), но в самом 
эндпоинте не читала заголовок `Idempotency-Key` и не использовала поле 
при создании платежа. В результате повторный запрос с тем же ключом 
создавал новый платёж.

**Как заметил:** Сравнил с сгенерированным кодом — 
функциональности не было. Проверил curl'ом: два запроса с одинаковым 
ключом создавали два разных платежа.

**Как исправил:** Попросил модель добавить проверку `Idempotency-Key` в 
начале функции `create_payment` и передавать значение ключа в модель при 
создании.
